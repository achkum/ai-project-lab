Thesis · for review

Can a small model recognise the conditions hidden inside an “approval”?

Study a task-specific model that flags conditional, ambiguous or superseded approval text for human review. It must never authorise a merge or infer who actually made a decision.

Why now

The October 19 case study reports a concrete mismatch between review wording and recorded approval state.

  1. Review text + event context
  2. Rules vs small pretrained text model
  3. Flag condition / abstain + cite evidence

Concrete recent failure; research gap and dataset unconfirmed

Explore scope, alternatives and stop criteria

Question to test

Does adapting a small text encoder improve conditional-approval recall over rules, while keeping false alarms low on unseen phrasing and projects?

Evaluation / customer test

Compare regex/rules, TF-IDF + logistic regression, frozen sentence embeddings and a small adapted encoder. Split by author/template and scenario family; measure precision, recall, calibration and abstention coverage. Include negation, resolved conditions and harmless suggestions.

Data and access

First create a labelled synthetic feasibility set; it cannot establish real-world performance. A thesis requires consented or appropriately licensed review examples, independent annotation and a leakage-safe held-out set. These are not secured yet.

First week

Produce annotation guidelines, 50 independently checked pilot cases and a baseline confusion matrix. Stop if reviewers cannot agree on labels or rules already solve the task.

What already exists

GitHub already supports requested changes and independent review; the case study recommends those practices. This would be an aid for ambiguous legacy text, not a replacement for proper controls.

Our proposed difference

Our proposed contribution is a bounded comparison of extraction and abstention under wording shift. It is not invention of conditional review or secure approvals.

Possible business path

Possible reviewer-assistance component for an AI-Org reliability service. No buyer demand or standalone market is established.

Reasons to stop

Drop if a closest-work search finds the same evaluation, real data cannot be obtained, or a simple rule performs equally well. LTU supervisor acceptance and study design remain to confirm.

Resources and scope

Applied NLP / custom small model. CPU baselines first; adaptation runtime must be measured before committing.

Thesis · for review

Does a contamination detector confuse familiarity with prior exposure?

Stress-test existing forecasting-model audit methods with controlled examples that separate exact prior exposure from unseen series sharing the same generating process.

Why now

The October 15 model release and October 17 disclosure question make evaluation uncertainty current. September research and the older TSFMAudit method are essential counterevidence.

  1. Controlled seen / unseen series
  2. Adaptation probes + reference baselines
  3. Measure false accusations and uncertainty

Current trigger; narrow contribution and runtime unconfirmed

Explore scope, alternatives and stop criteria

Question to test

Under a fixed local compute budget, how reliably do adaptation-based audits separate deliberately exposed sequences from new same-process sequences?

Evaluation / customer test

Use small, dated synthetic series generated after model release and controlled adaptations with known exposure. Compare static loss, candidate-only probes and reference-debiased probes. Hold out generating-process families. Measure false-positive rate on unseen familiar processes, sensitivity and compute cost.

Data and access

Original synthetic generators allow known exposure in the controlled adaptation stage. They do not reveal a foundation model’s actual pretraining corpus. Verify one checkpoint licence and implementation access before downloads; no paid compute.

First week

Inspect the existing audit implementation, map exactly what it already tests, and time one smallest-model probe. Produce a go/no-go report. No full benchmark or large-model fine-tuning in week one.

What already exists

TSFMAudit already debiases for dataset difficulty and tests transformed duplicates. The September study already discusses domain familiarity. A generic contamination benchmark would duplicate prior work.

Our proposed difference

The proposed test targets known adaptation exposure versus new same-process samples under a small compute budget. Whether this adds anything beyond existing ablations must be established first.

Possible business path

Could inform a specialist model-evaluation service for customer-specific deployments. Commercial value is hypothetical; do not sell contamination certificates.

Reasons to stop

Drop if existing code already covers the proposed distinction, controlled ground truth cannot isolate the factor, or even the smallest probe exceeds laptop resources.

Resources and scope

Non-LLM model adaptation / evaluation. Higher feasibility risk than RT1; research-only until the pilot passes.

Project · for review

A read-only review-evidence checkup for teams using coding agents

Turn a repository’s exported review events into a small, inspectable report of what is supported, contradicted or unknowable. Sell the usefulness of the review, not a claim that AI can prove human judgement.

Why now

October case evidence makes this timely; existing GitHub guidance and Kosli mean the opportunity, if any, is a lightweight diagnostic service.

  1. Import exported PR events
  2. Check revision, time and stated conditions
  3. Show evidence gaps + existing remedies

Reported operational problem; service demand untested

Explore scope, alternatives and stop criteria

Question to test

Would a small team use this report to change one concrete review or credential practice?

Evaluation / customer test

Implement fixtures for stale approvals, checks finishing after merge, ambiguous actor identity and conditional text. Compare findings against manual inspection and native GitHub controls. The report must say unknown when evidence is missing.

Data and access

Start with synthetic event bundles and this owner’s explicitly selected test repository if later authorised. No employer data, secret scanning, production permissions or automatic repository changes.

First week

Build a complete local import → evidence timeline → export journey in 3–5 days, with a documented fixture suite and a walkthrough. A later owner-led trial with two maintainers tests usefulness.

What already exists

GitHub rulesets and identity separation prevent many failures. Kosli already collects delivery evidence. Prefer configuring existing tools when that solves the problem.

Our proposed difference

A narrow, local diagnostic and onboarding deliverable. It is explicitly an integration/service hypothesis, not a new approval protocol or compliance certification.

Possible business path

Potential fixed-scope setup/reliability review for small development teams; repeat maintenance only if customers identify recurring value. No willingness-to-pay evidence yet.

Reasons to stop

Drop if the report adds nothing beyond native settings or an existing tool’s report, or maintainers will not use it. Do not build another general agent platform.

Resources and scope

One-week product experiment; deterministic checks first. Optional classifier only after RT1 evidence supports it.

Project · for review

A forecast pilot report a customer can actually challenge

Package one model pilot so a customer can inspect data dates, baseline fairness, uncertainty and known disclosure gaps before accepting a headline accuracy claim.

Why now

October’s small-model release and linked evaluation discussion show why a model ranking alone leaves important questions unanswered.

  1. One dataset + existing evaluator
  2. Check dates, baselines and missing disclosures
  3. Produce a client decision report

Timely technical need; product gap and demand unvalidated

Explore scope, alternatives and stop criteria

Question to test

Does a transparent pilot report help a prospective custom-model customer choose between a simple baseline and adapting a pretrained model?

Evaluation / customer test

Use fev outputs or a small equivalent baseline run; separate measured outcomes from supplied metadata. Display model-release date, target dates, model hash, evaluation window, latency and uncertainty. Missing corpus disclosure stays unknown.

Data and access

First ship an honest sample report with synthetic data and real baseline calculations. Any pretrained run must pass licence and CPU timing checks; never populate model results with invented predictions.

First week

Deliver a local data import → baseline evaluation → evidence report in 4–6 days. The finished slice is one decision report, not a leaderboard or training platform.

What already exists

fev already provides tasks and summaries; post-release evaluations already exist. Existing tooling should do the numerical work. Generic forecast dashboards are not the opportunity.

Our proposed difference

A proposed client-facing interpretation and evidence layer around an existing evaluation. No novel metric or contamination detector is claimed.

Possible business path

Possible entry deliverable for a custom-model consultancy. Buyer access and value are untested; a client conversation is necessary before building recurring infrastructure.

Reasons to stop

Drop if existing fev reports answer the customer’s questions, no customer will share a usable dataset, or the report does not change a decision.

Resources and scope

One-week service prototype. No API fees, GPU provisioning or paid model access.
